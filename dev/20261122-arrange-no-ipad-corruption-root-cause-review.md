# 2026-11-22 自御共享配置再次损坏：未打开 iPad 仍复发的原因与恢复复盘

**用途**：供「自御 v2 多设备同步与存储架构优化」专项会话读取、与 11 月 21 日已提出的方案合并评估。本文为已发生事故的事实与技术边界，不是新的开发指令；未实施 v2，也不建议继续靠每次人工修复运行。

**结论**：用户明确说明 11 月 22 日早上未打开 iPad。这个事实不与事故矛盾。当前最明确的系统性问题是：GVKit 把待办全量排序、跨天目标、特别提醒日期、界面设置等**多个独立业务状态都放在同一个可变 Markdown YAML 文件**，并依赖无业务语义的 Obsidian Sync 文本合并；合法的并发/延迟更新有机会产生非法 UUID、重复 YAML 键或损坏结构。**无需同一天主动打开 iPad**，仅手机与其已有本地版本、远端历史版本及 Headless Sync 的同步/合并也可能形成版本差异。11 月 15 日新增的「当天首次进入自御时自动处理特别提醒置顶」是一项已查明的自动写入入口，值得作为复发诱因重点复验，但**尚无直接证据证明是它或某台设备在本次制造了坏文件**。

## 2. 10:20 坏版本具体坏在哪里

文件：`settings/gvkit/arrange.md`。

- 排序 `order` 有两个本来有效的 UUID 片段被错误拼接成一个超长字符串（其中一条呈 `01a1fc89-…-027c8a-1f6d-…` 的连续粘连形态），同一排列里还重复插入已有事项 ID；坏版本表面 266 条排序项，只有 264 个唯一字符串，并含非法 UUID。

- 同一坏版本还将 `specialReminderDay` 从 11 月 21 日改为 11 月 22 日。此项是**当天首次进入自御的自动提醒处理**可能产生的正常业务变化，但与损坏同时出现不证明其执行方或合并位置。

## 3. 为什么不打开 iPad 仍然会发生？

**不是「必须多设备当天同时手动编辑」才可能出问题。**

1. **手机打开自御就可能自动写同一配置。** 当前源码 `src/arrangeStore.ts`：
   - `loadInner` 若发现 `dailyGoal.day < today`，执行 `day_rollover`，可同时把昨日未完成目标移到排序前面、更新今日目标/返回 ID，并调用 `saveState`。
   - `enter` 在当天首次实际展示自御时，若 `specialReminderDay !== today`，自动重新整理提醒顺序、更新当天日期，调用 `saveState('special_reminders')`。该入口由 `src/arrangeView.ts` 的 `view_open/view_enter/visibility` 路径触发，**不是用户需要手工点「置顶」才会写**。
   - 11/15 提交 `c6736c4` 引入每日提醒自动处理；11/19 的 `5945bdb` 仍保留此写入机制。
2. **跨设备同步是历史延迟版本的协调，而不只看是否刚打开过 iPad。** 一台之前编辑过的设备可带着尚未送达的版本在后来同步；仅手机与云端/Headless 之间的版本分歧，也可能触发文件冲突/合并。不能因为 iPad 今天未被手工打开，就把它认定为本次写入者；同样也**不需要假定** iPad 本次参与了写入。
3. **本地安全写入不等于跨设备安全合并。** GVKit 0.6.77 的 `saveState` 用 `vault.process` 读取本机当前文件并按更改字段校验，能降低同设备错写；但远端 Obsidian Sync 仍按 Markdown 文本行合并，**不理解 YAML 的对象、UUID 唯一性和排序的业务语义**。这两层保护不等价。
4. **设备来源仍未知**。Headless 的 `Push/Accepted` 只说明收到更新，不标识最终修改由 iPhone/iPad/其他桌面客户端/云端冲突合并生成。必须有对应端 Sync Activity Log 和 GVKit 设备本地 Trace 才能进一步锁定。

官方说明：https://obsidian.md/help/sync/troubleshoot —— Markdown 默认使用 diff-match-patch 自动合并，同步冲突可导致重复内容或格式错误；https://obsidian.md/help/sync/settings —— 冲突策略及设置由每台设备分别配置。

## 4. 为什么最近显得更频繁？按证据排序

**已证的系统变化：**
- **集中共享文本增长**：约 10/24 时 258 字节、排序 1 项；11/20 时超过 12 KB、排序约 256 项。全量 UUID 顺序、目标和偏好混在同一频繁重写的 Markdown 内，使文本补丁的边界更多更近；这是合理风险解释，尚没有对当前具体冲突概率的因果测量。
- **自动写入路径增加**：11/15 新增 `specialReminderDay` 与提醒置顶，意味着每天首次进入自御有独立写配置场景。跨天目标原本也可自动写。两类写可能在设备启动、恢复可见或刚同步时相互接近，**属于重点验证的触发条件**。
- **异常可见性升级**：11/19 引入/强化 `validateConfig` 和异常保护；有损坏时现在明确显示「配置异常」并暂停目标确认。更容易看到错误，不等于全部坏文本都是新产生的。
- **现场异常确实集中**：11/19～11/22 连续有坏版本记录和人工修复。此前 11/10、11/12 等也有异常，但近期集中程度需要分开看「实际损坏次数」「同一个坏版本持续多久」「用户看到几次警报」；不能把备份的每个坏版本都算成独立故障。

**不支持的简单归因**：独立 Git 备份记录同路径发生改变的快照数：10/24～10/31 = 83、11/01～11/09 = 87、11/10～11/17 = 88。这三段并没有显著递增，故**不能说最近只是因为频繁修改配置才突然多故障**。快照按实际变动采样，并非每个设备每次写操作的完整日志；该统计只用于排除「已观察到显著写频暴涨」的说法。

**综合判断**：最有解释力的是「既有存储/合并设计缺陷 + 文件结构扩大 + 新增自动写操作」，可能叠加更严格的异常提示。这是系统性成因分析；本次具体损坏写入者和完整事件链仍不确定。

## 5. 本次成功恢复方式与证据

1. 保留 10:20 的原始坏文件快照（`1251d61`），不直接用旧整文件覆盖当天新数据。
2. 受控写入时按正式文件当前 SHA 检查，仅删除非法拼接 UUID 和重复序列项，并恢复 `dailyGoal.returnedId`；保留当天已变化的 `specialReminderDay: 2026-11-22`、其他合法排序与全部界面配置。
3. 读回验证：263 个合法不重复 UUID、正常 `dailyGoal`、YAML 结构恢复；12:26:45 Headless 上传成功。
4. 制作人手机自御小省略号菜单选择「刷新」后确认恢复。12:29 文件仍有效，正常业务更新已继续同步。

**注意**：靠人工修复快照只能应急，不是未来产品必须依赖的日常工作流；不建议让用户为了安全被迫放弃自然多设备使用。

## 6. 提交给 v2 方案会话需要综合判断的重点

这次故障应该成为 v2 的**必验案例**，而不是开一个新的独立平台或继续增加零散补丁：

- **完整覆盖「只有 iPhone 今天打开自御」的情境**：iPad 没在当天打开、Headless 持续在线、手机携带前日遗留状态、今天首次进入触发 `day_rollover` 和 `special_reminders`，确保不会出现非法结构或数据丢失。再覆盖真实双设备离线并发以及旧版本客户端重新上线。
- **避免同一大 YAML 文件被不同业务动作反复改写**。现有候选 `dev/20261121-arrange-v2-storage-proposal.md` 的「分领域状态 + 唯一不可变操作 + 可重建投影 + 一次性权威切换」方向与此事故吻合；仍需验证操作记录数量、启动速度及多端实际行为，勿为假设场景打造重型同步服务。
- **跨天目标返回与顺序移动必须按一次业务意图提交和投影**，每日提醒同理；仅看当前端 `vault.process` 的 SHA/字段比较，不能代替跨端合并的语义校验。
- **单条损坏不应锁死全部自御**。即便数据到达顺序异常，也应保住其它事项、设置、编辑与奖励事实；保留有效数据与现场，隔离问题操作/状态。
- **旧版设备迁移**：不能指望新手机升级后使未升级旧 iPad 自动停止写旧协议；必须保证旧文件不能重新污染新权威，留存旧端迟到操作的恢复/冲突通路，而不是新旧状态双写。
- **有明确必要的最小诊断**：再次发生时，只读取得手机/桌面对应时间的 Obsidian Sync Activity（尤其 Merge Conflicts）与菜单「复制交互诊断（含配置 Trace）」，对照服务端原始修订和 SHA。当前 GVKit Trace 主要记录异常而非每次成功写入，无法仅靠 Headless `Push` 判断源设备。将来如确有必要，在**相关异常路径**补触发动作、端标识/版本、前后指纹和时间即可，避免全局流水日志平台。
