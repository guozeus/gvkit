## 真实身份与排序语义（依据 src/arrangeStore.ts / arrangeCore.ts / fileIdCore.ts）
- gvid 是文档/事项的稳定 UUIDv7 身份；UI 和产品文案可称“事项 ID”，底层 UUID 只是编码方案。每个正常事项文档一个 GVID，重复事项的每个执行实例另有 occurrence/instance ID，并非同一个文档拥有多个 GVID。
- settings/gvkit/arrange.md 的 order 不是本文件身份，而是仍未完成事项的 ID 数组。pendingOrder 只保留尚未完成的 id；普通已完成事项保存为 安排/已完成/*.md，显示依完成时间排序；归档迁入 安排/历史/，并非无限堆进全局 order。重复事项历史按实例/历史规则保存，独立于普通 order。
- 大量 UUID 本身不是规模瓶颈；现有负担是：几乎全部偏好、每日目标、排序存于同一共享 Markdown，并可能在改一个字段时重写全文；普通加载扫描并读取待执行/已完成原件；pendingOrder 里逐项 order.indexOf 存在 O(n²) 行为。数千、数万事项后，单纯扩大 order 数组与全量读取不合适。

## 制作人明确方向（待专轮设计/制作，不在本轮修改）
1. 配置按真实业务领域拆开，变化频率高的与很少变化的分开；尽量不再为单项操作修改整个共享文件。
2. 持久事项继续按自身唯一 ID 管理，不把历史完成事项长期累积到一个巨大排序数组；待执行排序应有独立、按需维护、规模可扩展的机制，支持现有置顶与钉住槽位语义。
3. 每日目标、排序、界面偏好、奖励/提醒按各自一致性需求存储。拆文件有助于减少冲突，但必须处理不同设备同一字段并发写入；简单换扩展名为 JSON 非万能解决，默认最新修改胜出可能静默丢改动。
4. 先验证旧数据无损迁移、实际多设备同步和已证正确 UI 行为，再进行明确一次性的存储切换；避免通用同步平台、复杂身份层和其他无关开发。
5. 重要普通笔记沿用 Obsidian Sync 与独立 Vault Git 备份，切换设备推荐确认上传/下载完成；不自动改变所有设备的冲突策略。
