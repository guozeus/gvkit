# GVKit 自御 v2 多端安全存储候选方案（2026-11-21）

状态：设计建议，未实施、未切换正式数据格式、未变更任何正式事项/配置、未发布。该方案以制作人“任何设备打开自御都不会因共享配置异常而瘫痪；老设备版本滞后也不破坏新数据；继续正常多端使用；未来数万事项仍高效”为目标。

## 已核实的现状与外部约束
- 现行 GVKit 0.6.77 仍以 settings/gvkit/arrange.md 作为包括排序、每日目标、界面设置、奖励开关等多个领域的**同一个可变权威文件**。YAML 异常会使保存动作受阻，并可能显示默认设置；11月19–21日已经有真实坏版本和独立恢复记录，详见 dev/20261119-arrange-sync-resilience.md、dev/20261120-arrange-config-recovery.md、dev/20261121-arrange-ids-order-and-sync-review.md。
- Obsidian Sync 对 .md 冲突自动执行文本合并，对一般非 Markdown 文件通常最后修改胜出；非 Markdown 扩展名需逐端启用 Sync all other types；设置本身不跨设备同步。官方：https://obsidian.md/help/sync/troubleshoot 和 https://obsidian.md/help/sync/settings 。
- 11月19日隔离原版 Headless Sync 合并函数已证合法输入可能变为非法 YAML；真实每次故障的原始双端文件尚未完整取证。只改扩展名不能保证并发修改无损。

## 建议的最小正确形态
1. 各事项保留各自 GVID（UUIDv7），其业务名称叫“事项ID”；重复事项单次实例保持独立实例ID。**身份机制不变**。
2. 分离界面偏好、每日目标/跨天返回/提醒、奖励、事项属性/完成、未完成排序、已完成历史，不再向单一共享 YAML 重写整份状态。跨域有关联的更新（比如跨天返回同时调整排序与目标）保持为一条原子业务意图，不能硬拆致半成功。
3. 避免多设备改同一可变文件：每次真实操作产生一个有独立ID、只创建一次、不会再修改的结构化变更记录（本机先持久保存，交 Obsidian Sync 传输；每端收到后按ID去重并重建当前状态）。按领域目录归档，不能以设备钟表判定冲突的必然胜者；互不相干字段自然合并，同一字段或同一排序目标的并发修改保留双方意图，自动解决可确定的情形，无法判断时只标记涉及的那一项，绝不静默丢操作。
4. 具体承载格式先用两台真实隔离客户端验证。优先选择无需用户手工开启逐端特殊同步开关的传输载体。可评估每操作独立只创建一次的 Markdown 文件（虽然 .md 会文本合并，但不存在同路径并发重写就没有该合并源），同时测量大量文件索引成本；若使用 JSON，先证明相关设备“Sync all other types”实际启用并同步到达。不以“换成一个可变 JSON”冒充根治。
5. 未完成排序记录尽量表达一次移动/置顶的操作及其锚点/相对位置，不维护全量随每次变动改写的 UUID 数组；投影后必须保持已认可的“钉住槽位”和置顶语义。已完成与历史不参与未完成排序；完成/提醒/日期等高频机器状态亦应避免反复整份覆盖。对于用户主动在 Obsidian 文本编辑器修改事项正文，仍须遵循普通 Markdown 的冲突语义：可保护自御不整体瘫痪并尽可能独立保存业务状态，但不能承诺离线两端随意编辑同一段正文都能自动语义无损合并。
6. 本地维护可重建的快速索引/最后有效投影：先显示首屏必需事项，再按需读其余正文；数量来自完整轻量索引而非已渲染行数。数据损坏、迟到、乱序、重复时不把异常结果写回共享文件；校验独立操作，隔离有问题的记录，从其余有效操作或确认快照重建。设备离线时操作须先耐久落盘再反馈成功，回线后幂等汇合；不要用陈旧本机快照强盖云端。
7. 操作日志随时间增长；索引和必要的已确认快照可压缩，**未证明离线设备全部收到时不能随意删除仍可能需要的记录**。先验证1万以上待办及大量完成历史的启动、排序、同步表现，再选择必要的简化压缩机制；不得为假设的极限规模搭建重型系统。

## 旧版本过渡的严格限制
- 新版先只读导入旧配置并保留原始版本与本机未完成意图，影子验证内容和顺序；通过真实手机/iPad/PC隔离交互测试后，进行一次明确的权威切换。新版以后**只使用 v2 权威，不再把旧 arrange.md 的文本合并结果当作新配置**；不能新旧双写。
- 能使旧插件识别的不兼容版本标记，可让“已收到标记”的旧插件只读/报旧版，但**不是远程强制锁**。完全离线、未收到标记的旧插件仍会按旧协议写旧文件；之后的 Obsidian Sync 可能损坏旧文件。新版须隔离该旧文件，检测其可能包含的迁移后操作，有歧义就保留原始版本和待确认意图，不能静默当作当前正确值，也不能盲目全部自动导入。
- 仅靠升级任意**一台**设备，无法修改尚未升级设备的旧代码，无法从底层阻止旧设备写旧格式或保证它的离线修改一定完整到达。保证**新权威不被旧格式污染**可以做到；若要求**所有旧设备写入也无损自动合并**，必须做一次已知设备升级/切换确认或有能够拒绝旧协议写入的服务端权威机制。当前推荐前者，暂不另造服务器。
- 升级体验尽量自动且一次性：新版发现旧库就先保护快照、读取投影和执行迁移；对于已知设备尽量自动验证状态、完成切换；需要用户介入时只提示真正存在的不可自动合并的旧版离线操作，而非反复弹同步提示。

## 实施与验证顺序
A. 先在开发机只做新读取器、不可变变更的合并投影、兼容迁移（正式旧权威保持）；确认界面偏好不同字段、同字段冲突、跨天原子组合、排序/钉住语义。
B. 两台真实隔离 Obsidian Sync 端验证离线分别修改、消息乱序/重复/延迟、启动中途到达数据、设备久离线后恢复、损坏一条记录、旧版重连及再升级；不改正式库。
C. 保护正式配置/历史并确认已知设备升级与待同步动作；一次切换 v2 权威，发布 GVKit 新版，手机/iPad/PC体验。必要时以旧合法版本回退，切勿将旧新两套同时当权威。
D. 最终验收：任意设备打开不会因旧配置损坏回退字体或锁死勾选；不同设备改不同设置均保留，同一设置冲突不静默丢失；离线修改最终被合并或明确保留为冲突；完成/钉住/每日目标/奖励原有体验正常；数万事项打开首屏不全量读正文，计数依旧准确。

## 一句话设计决策
采用“分领域业务状态 + 唯一不可变操作 + 本地快速投影 + 一次性版本切换 + 单项隔离恢复”，而不是“把一个大 arrange.md 换成若干仍可互相覆盖的可变 JSON”，同时保留现有 Obsidian Sync 和 GVID 身份。

## 2026-11-22 单设备打开复发专项复核与 v2 必要补强
依据：dev/20261122-arrange-no-ipad-corruption-root-cause-review.md 与 dev/20261122-arrange-phone-config-alert.md。此处是对本提案的具体覆盖性审查，尚未实施。

### 综合结论
**核心方案可以覆盖此次同设备打开也报错的故障，不必推翻。** 但是要将“本地启动时已持有非法/陈旧数据”和“当天首次打开自动产生跨天/提醒写入”升级为首要验收路径，不可只测试两台设备同时手动操作。

### 关键事实
- 2026-11-22 北京时间09:41左右 iPhone 已报错，而09:42开发机正式配置合法，故“本地视图/未到达或暂时损坏的本地版本”是真实需要覆盖的启动场景。
- 10:11 Headless 通过 Sync 收到更新，10:20快照出现 UUID 拼接/重复及 dailyGoal 字段破碎，12:26受控修复后上传正常。没有证据锁定某个设备或单一写入入口。
- 现行 GVKit 在 loadInner 中执行 day_rollover（可能同时变更当日目标及全局 order），在 enter 中执行 special_reminders（当日首次进入修改提醒日及 order）；view_open/view_enter/visibility 等可能调用 enter。并不需要用户手动触发写操作；11月15日引入的每日提醒自动整理增加了一条写共享配置的入口。
- 官方 Sync 明确说明“启动时自动创建或修改笔记，远端短时下载可能直接取代本地初始版本”（https://obsidian.md/help/sync/troubleshoot）。必须作为真实测试条件，不能把“今天只开一台设备”误当作没有版本协调风险。

### 必须补强而非额外造系统
1. **启动隔离**：打开自御首先从本机已验证投影/未确认操作展示现有正确状态，独立读取新增操作，等待同步增量按ID合并；不能让“旧版共享 YAML 文件不存在/暂时非法/尚未到达”的单项错误自动重置字体、每日目标或锁死正常事项勾选。损坏且无法重建的单元只隔离该单元，保留本机已知正确状态、操作原文及可恢复快照，不把猜测的默认值写回共享层。
2. **首次进入/跨天幂等**：只读加载、可见性切换、重新打开不应无条件生成新的共享写入。确需改变业务状态时，基于“业务日期+目标/提醒上下文”的稳定**业务幂等键**执行一次明确业务操作；不同设备同时触发同一天更新后按业务语义去重，而不只依赖两个不同操作 UUID。跨天目标返回与排序前移必须是同一业务意图；特别提醒当天整理也保持自己的原子意图、明确与跨天排序的先后语义，避免中途只生效一半。
3. **旧端/远端到达顺序**：即使没有操作 iPad，手机历史待上传、本地旧投影、持续在线 Headless 及此前其他设备离线动作都可能造成延迟到达；任意顺序、重复、旧数据覆盖均应在 v2 投影器里可识别，旧 arrange.md 在 v2 切换后永不成为权威。旧设备未收到版本标记前仍有能力写旧文件：新版只能防新状态被污染，不能神奇保证旧版未同步的全部历史操作都无损可回收。
4. **提交前后校验和自动恢复**：每条新操作独立校验身份、业务值与依赖，只有在本机持久落盘后才向用户反馈成功；接收方按ID去重、隔离坏操作、从已确认投影及有效记录重建；需要对日期、排序等跨域状态整体验证。真正不可判定的并发操作保留证据，不允许静默随机覆盖。无需为此搭建通用日志/守护平台。
5. **明确可保证范围**：v2 能使**配置域**对旧版 YAML 同步破坏免疫，并使自动写入可重放、可恢复；不能承诺 Obsidian 普通 Markdown 正文在所有离线同段编辑冲突下永远无损，或一台尚未升级的旧客户端自行按新协议运转。事项内容的原件仍需保留已知安全的备份/冲突语义。

### 专门增加的四个必验案例
- **11/22原样场景**：9:41手机本地异常、同时远端配置有效；10:11远端迟到坏旧版本；手机不开 iPad、自动跨天和特别提醒同日触发；不重置字体/锁死勾选、不向新权威传播旧坏 YAML，旧合法业务意图能恢复。
- **同机反复进出**：同一天 view_open、visibility、day_tick 各重复多次，只产生一次当天需要的逻辑变更，且跨天目标+排序不半提交、奖励不重复发放。
- **新旧端回线**：未升级旧端离线后写旧 arrange.md、后来同步/升级；新版仍可正常打开，旧端的确定性合法意图可拾取，有歧义的保留待处理，不被静默覆盖。
- **大量事项性能**：10,000+待办与大量历史，首次打开按需索引、排序及奖励数字正确；文件数/操作数对手机同步时间与容量的影响可接受，且不会因“每次打开都要全量重放”退化。

本轮仅将新事实纳入方案，没有变更 GVKit 业务代码、正式 Vault 或发布版本。

## 2026-11-22 两轮独立审核最终共识（当前有效）

本节是审核后正式可行动结论，覆盖文内较早的相抵触候选。独立审核首轮提出六类协议缺口；第二轮同一会话赞同分阶段最小方案，反对首版进行所有事项业务状态迁移或预先开发完整打包系统。独立全文：dev/20261122-arrange-v2-independent-review.md。

### 目标和边界
用户任意设备打开自御，即使本地先坏、迟到同步坏版本、旧版设备回线或首次进入自动处理每日目标，不能再整套配置恢复默认或阻止独立事项勾选。须保住合法业务修改，问题只隔离在对应记录和其依赖范围，且有足够证据定位。首版不承诺所有普通Markdown正文、重复历史或旧版离线写入都自动语义无损；相关事项机器状态以后专项补齐。保留GVID、现有Sync与独立Git备份，不另造通用同步平台。

### 阶段0：先补关键写入诊断（小版本，业务逻辑不变）
在现有 ArrangeTrace 增加少量必要的成功写入边界：设备/会话标识、插件版本、UTC及run/seq、原因、源和候选与写后读回的文件指纹/校验结果、外部文件变化、错误阶段及恢复来源。设备本地有上限轮转、异常证据冻结；自御无法打开也能导出；不保存正文、凭据或普通点击流水。可区分插件候选已坏、写入不符、写后被外部替换或加载失败。仅凭本插件仍不能证明Obsidian Sync内部哪个部位合并错误，需要对应端Sync Activity和历史版本。

### 阶段1：配置域独立操作和正常启动
偏好、每日目标/返回、特别提醒、奖励配置、待办排序分领域；每次业务修改记录为独立不可变且不同路径的操作，重试沿用原操作ID，不再重写一整份共享YAML。首选验证无需额外逐端开关的独立Markdown记录；不能直接将一个JSON覆盖文件当作根治。每条操作含格式版本、统一激活基线、操作ID、目标、业务参数、相关因果前置、自动业务幂等键。对内容相同的同ID去重；同ID异内容隔离。各端以已确认基线加有效操作集合确定性投影，不按文件到达顺序或设备时间选择冲突胜者。同字段冲突保留双方，不影响其他字段。

跨天业务键由激活批次、动作类别、统一库时区业务日构成，原目标版本/上下文作为前置。同一业务日跨端重复触发不得重复生效，不同旧目标不得错误合并。跨天目标返回和排序移动为一次逻辑原子意图；同日特别提醒为另外一次，明确先跨天后提醒，迟到自动动作不覆盖较新的人工调整和已选目标。只读加载及重复进入不能无条件生成新写入。

先用本机最后经校验投影正常展示，首次打开、前台恢复、相关文件变更和写入前后进行有界增量检查，不等待一个可能无法可靠判定的全局Sync完成状态。未收到激活记录/必要数据不等于库为空，不得创建第二套迁移基线或写默认值；目标、计数、依赖缺失显示待确认。独立完整的事项继续可以操作。坏操作或坏事项保留原始证据，仅隔离受影响事项与其父子完成、目标、重复、奖励和准确计数等依赖，绝不能简单跳过坏事项后错误允许父项完成或重复奖励；正常事项继续可用。

### 阶段1：一次性旧版权威切换
新客户端先保留旧数据和已知设备待同步意图，创建一次统一激活记录，各端接同一个版本基线，不同时读写新旧权威。切换后旧 arrange.md 即使被旧设备重新同步也不能污染v2。迟到旧变更以迁移基线比较，确定无竞争者自动导入且避免重复，歧义保留原件供最小范围处理；完全离线未升级设备不可能被新版强制停止旧协议，也不能保证其全部历史修改可无损取回。v2已产生新操作后不能直接恢复旧权威丢掉新数据，必要回退须具备v2读取和保全或转换能力。

### 阶段2：事项业务状态与规模优化
先确保首版单事项错误不致全局瘫痪，后续把插件维护的完成/撤销、日期、父子、钉住、重复记录和奖励事实逐步迁入有因果语义的操作投影，现有自由Markdown正文仍保留冲突与备份边界。索引与正文按需加载、待办排序避免反复全量重写和低效indexOf。事件格式为以后不可变打包预留身份/因果，首版不实施完整打包，也不随意删除旧记录；在真机测量一万待办、数万操作后若超过事先固定预算，才将打包纳入发布必要工作。

## 2026-11-23 排序模型再校准（稀疏排序与单项持久修改）

制作人指出：处理一个特别提醒事项，不应该重写所有待办的全局序列，理论上只需改动相关事项的排序位置。此判断正确，是 v2 设计中应明确落实的持久化边界。

### 已核代码事实
- 当前 src/arrangeCore.ts 的 reminderTopInOrder() 从完整 order 数组筛选全部未完成的特别提醒，按 specialReminderAt 时间排序，保留其他已钉住事项占据的槽位，然后返回全量新 order。这是现有明确的用户体验语义，不是单个提醒必定只移动一项。
- src/arrangeStore.ts 的 enter() 每个新业务日都把 specialReminderDay 更新为今天，并调用 saveState('special_reminders')。即使算出的 order 内容未变化，只改日期，saveState 仍从旧 arrange.md 完整解析与重新序列化整个 YAML 文档；如 order 变化，整个全量 order 也会随之重写。
- 因此需区分：在内存中计算完整展示顺序（可接受）和把全部事项ID重新序列化到一个被 Sync 文本合并的全局文件（应废弃）。

### v2持久化建议
- 保留每事项独立GVID身份；排序是独立于身份的 rank/position，不是序号1..N。可采用有空隙的排序键（稀疏数值、分数索引、LexoRank类按字典序排列的键），移动一项只改变它的排序键，其他项不需要全部重新编号；成熟参考 Atlassian Jira LexoRank https://confluence.atlassian.com/adminjiraserver/managing-lexorank-938847803.html 和 Figma fractional indexing https://www.figma.com/blog/how-figmas-multiplayer-technology-works/ 。
- 但是**不要直接把rank写成一个会被多台设备反复改的共享Markdown字段**，否则多端对同一事项排序仍可出现文本冲突。应沿用已审核v2的不可变操作：一次移动只保存“移动事项ID、相邻锚点/目标位置、受影响钉住槽位语义、因果基线”的单条操作，设备本机投影出rank；需要多项自动提醒时，一次业务操作可表示多项按提醒时间顺序前移，投影只更新真正受影响的少数项，而不是整份全局UUID排序表。真实同位并发依既定因果冲突规则处理。
- 特别提醒日期变更与真正排序变更分离：仅需要记录“今天已处理”的幂等业务状态时，不应触及排序数据；若需要重排，则生成有明确幂等业务键与时间顺序的独立排序意图。即使没有任何特别提醒应移动，仍不可重写全局排序。
- 必须保留现有已证的“钉住事项占据槽位”“每日特别提醒按开启时间排序”“用户后续手工置顶与移动不被迟到每日操作覆盖”体验。不是简单地在显示层永久让提醒覆盖用户手动排序。
- 理论上单项前移在常见情形只更改一个rank；若同一次合法业务意图涉及多个提醒或需要在个别区域重新平衡排序键，可以变更多个rank，但范围限于实际必要部分。避免绝对声称任何重排永远只需修改一条记录。
- 数万待办场景中内存排序/局部rank重建、增量索引与持久写入开销须分别测量；避免O(n²)的order.indexOf遍历成为瓶颈。
- 本轮是方案补充，不实施排序重构、不修改正式Vault数据或已安装GVKit版本。
