# GVKit 自御 v2 多端安全存储候选方案（2026-11-21）

状态：设计建议，未实施、未切换正式数据格式、未变更任何正式事项/配置、未发布。该方案以制作人“任何设备打开自御都不会因共享配置异常而瘫痪；老设备版本滞后也不破坏新数据；继续正常多端使用；未来数万事项仍高效”为目标。

## 已核实的现状与外部约束
- 现行 GVKit 0.6.77 仍以 settings/gvkit/arrange.md 作为包括排序、每日目标、界面设置、奖励开关等多个领域的**同一个可变权威文件**。YAML 异常会使保存动作受阻，并可能显示默认设置；11月19–21日已经有真实坏版本和独立恢复记录，详见 dev/20261119-arrange-sync-resilience.md、dev/20261120-arrange-config-recovery.md、dev/20261121-arrange-ids-order-and-sync-review.md。
- Obsidian Sync 对 .md 冲突自动执行文本合并，对一般非 Markdown 文件通常最后修改胜出；非 Markdown 扩展名需逐端启用 Sync all other types；设置本身不跨设备同步。官方：https://obsidian.md/help/sync/troubleshoot 和 https://obsidian.md/help/sync/settings 。
- 11月19日隔离原版 Headless Sync 合并函数已证合法输入可能变为非法 YAML；真实每次故障的原始双端文件尚未完整取证。只改扩展名不能保证并发修改无损。

## 建议的最小正确形态
1. 各事项保留各自 GVID（UUIDv7），其业务名称叫“事项ID”；重复事项单次实例保持独立实例ID。**身份机制不变**。
2. 分离界面偏好、每日目标/跨天返回/提醒、奖励、事项属性/完成、未完成排序、已完成历史，不再向单一共享 YAML 重写整份状态。跨域有关联的更新（比如跨天返回同时调整排序与目标）保持为一条原子业务意图，不能硬拆致半成功。
3. 避免多设备改同一可变文件：每次真实操作产生一个有独立ID、只创建一次、不会再修改的结构化变更记录（本机先持久保存，交 Obsidian Sync 传输；每端收到后按ID去重并重建当前状态）。按领域目录归档，不能以设备钟表判定冲突的必然胜者；互不相干字段自然合并，同一字段或同一排序目标的并发修改保留双方意图，自动解决可确定的情形，无法判断时只标记涉及的那一项，绝不静默丢操作。
4. 具体承载格式先用两台真实隔离客户端验证。优先选择无需用户手工开启逐端特殊同步开关的传输载体。可评估每操作独立只创建一次的 Markdown 文件（虽然 .md 会文本合并，但不存在同路径并发重写就没有该合并源），同时测量大量文件索引成本；若使用 JSON，先证明相关设备“Sync all other types”实际启用并同步到达。不以“换成一个可变 JSON”冒充根治。
5. 未完成排序记录尽量表达一次移动/置顶的操作及其锚点/相对位置，不维护全量随每次变动改写的 UUID 数组；投影后必须保持已认可的“钉住槽位”和置顶语义。已完成与历史不参与未完成排序；完成/提醒/日期等高频机器状态亦应避免反复整份覆盖。对于用户主动在 Obsidian 文本编辑器修改事项正文，仍须遵循普通 Markdown 的冲突语义：可保护自御不整体瘫痪并尽可能独立保存业务状态，但不能承诺离线两端随意编辑同一段正文都能自动语义无损合并。
6. 本地维护可重建的快速索引/最后有效投影：先显示首屏必需事项，再按需读其余正文；数量来自完整轻量索引而非已渲染行数。数据损坏、迟到、乱序、重复时不把异常结果写回共享文件；校验独立操作，隔离有问题的记录，从其余有效操作或确认快照重建。设备离线时操作须先耐久落盘再反馈成功，回线后幂等汇合；不要用陈旧本机快照强盖云端。
7. 操作日志随时间增长；索引和必要的已确认快照可压缩，**未证明离线设备全部收到时不能随意删除仍可能需要的记录**。先验证1万以上待办及大量完成历史的启动、排序、同步表现，再选择必要的简化压缩机制；不得为假设的极限规模搭建重型系统。

## 旧版本过渡的严格限制
- 新版先只读导入旧配置并保留原始版本与本机未完成意图，影子验证内容和顺序；通过真实手机/iPad/PC隔离交互测试后，进行一次明确的权威切换。新版以后**只使用 v2 权威，不再把旧 arrange.md 的文本合并结果当作新配置**；不能新旧双写。
- 能使旧插件识别的不兼容版本标记，可让“已收到标记”的旧插件只读/报旧版，但**不是远程强制锁**。完全离线、未收到标记的旧插件仍会按旧协议写旧文件；之后的 Obsidian Sync 可能损坏旧文件。新版须隔离该旧文件，检测其可能包含的迁移后操作，有歧义就保留原始版本和待确认意图，不能静默当作当前正确值，也不能盲目全部自动导入。
- 仅靠升级任意**一台**设备，无法修改尚未升级设备的旧代码，无法从底层阻止旧设备写旧格式或保证它的离线修改一定完整到达。保证**新权威不被旧格式污染**可以做到；若要求**所有旧设备写入也无损自动合并**，必须做一次已知设备升级/切换确认或有能够拒绝旧协议写入的服务端权威机制。当前推荐前者，暂不另造服务器。
- 升级体验尽量自动且一次性：新版发现旧库就先保护快照、读取投影和执行迁移；对于已知设备尽量自动验证状态、完成切换；需要用户介入时只提示真正存在的不可自动合并的旧版离线操作，而非反复弹同步提示。

## 实施与验证顺序
A. 先在开发机只做新读取器、不可变变更的合并投影、兼容迁移（正式旧权威保持）；确认界面偏好不同字段、同字段冲突、跨天原子组合、排序/钉住语义。
B. 两台真实隔离 Obsidian Sync 端验证离线分别修改、消息乱序/重复/延迟、启动中途到达数据、设备久离线后恢复、损坏一条记录、旧版重连及再升级；不改正式库。
C. 保护正式配置/历史并确认已知设备升级与待同步动作；一次切换 v2 权威，发布 GVKit 新版，手机/iPad/PC体验。必要时以旧合法版本回退，切勿将旧新两套同时当权威。
D. 最终验收：任意设备打开不会因旧配置损坏回退字体或锁死勾选；不同设备改不同设置均保留，同一设置冲突不静默丢失；离线修改最终被合并或明确保留为冲突；完成/钉住/每日目标/奖励原有体验正常；数万事项打开首屏不全量读正文，计数依旧准确。

## 一句话设计决策
采用“分领域业务状态 + 唯一不可变操作 + 本地快速投影 + 一次性版本切换 + 单项隔离恢复”，而不是“把一个大 arrange.md 换成若干仍可互相覆盖的可变 JSON”，同时保留现有 Obsidian Sync 和 GVID 身份。
