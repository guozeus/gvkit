二、必须修正

我认为有 5项需要在执行计划中明确修正。均可以在现有架构内完成，不需要增加新平台。

1. A3：排序不能简单采用单一全局 rank

问题：全局稀疏 rank 与固定钉住槽位不天然兼容。

现行代码 arrangeCore.ts:129–170 已有三套不同的排序语义：

普通移动：其他钉住事项保持原来的绝对槽位。

手工置顶、特别提醒：保留非目标钉住事项槽位，允许目标事项前移。

跨天目标返回：直接插入真正的队首，这是一个明确的例外。

例如，当前顺序为：

A → P(钉住) → C → D

将 A 移到末尾，正确结果应是：

C → P(钉住) → D → A

如果只把 A 的全局 rank 改到最大，结果可能变成：

P → C → D → A

钉住槽位就发生了变化。

建议直接修改 A3：

排序唯一权威为「迁移初始顺序＋不可变排序操作」。

操作分别表达普通移动、手工置顶、特别提醒批次整理和跨天目标返回。

本机投影重建展示顺序；稀疏 rank 只作为可丢弃、可重建的本地加速索引，不成为独立共享权威。

普通移动按照未钉住事项的相对顺序调整，再嵌入固定钉住槽位；特殊动作保留现行各自的槽位例外。

不为一次移动持久化整个排序数组。

推荐首版甚至不必引入正式 LexoRank 算法。

直接记录移动意图和相邻锚点，再重建本机顺序，反而更容易保持旧业务语义。只有实测本机排序索引成为性能瓶颈时，才需要优化 rank 的具体编码。

这既满足制作人的局部修改要求，也避免制造两套排序权威。

2. A4＋B3：自动动作还需要一条明确的优先级规则

目前计划已经规定业务幂等键，但还缺少自动动作与手工动作发生并发时的最终处理规则。

建议补充：

① 自动业务幂等

业务键包含：

激活批次＋动作类型＋库时区业务日

实际执行还必须检查其依赖的原目标版本、提醒集合和排序上下文。

同键、同业务效果只生效一次。

同键但前置状态不同，不能随意选其中一条覆盖另一条；应根据因果关系判定是否等价，否则保留相关冲突。

② 原子操作

跨天目标返回及其排序调整必须共同成功或者共同不生效。

特别提醒整理也是一个完整逻辑操作，内部可以包含多个事项的位置调整。

如果今天没有实际排序变化，只记录必要的今日处理状态，不产生排序操作。

③ 手工操作优先

这是目前最需要补充的部分。

建议规定：

同一业务日内，同一事项发生并发自动排序和明确手工排序时，手工排序意图优先；迟到自动操作只补齐仍适用的业务效果，不得反向覆盖手工结果。无法安全合并时保留该事项的排序冲突。

判断依据是业务日、操作类型及因果前置，不是文件到达时间。

同时，跨天动作使用配置投影确认的库时区；如果时区本身处于冲突状态，暂缓对应自动业务，不阻断其他事项。

这可以解决重复打开、双端同日触发以及手工调整后迟到自动覆盖三个问题。

3. B1＋B2＋C1：明确激活基线与本机持久化合同

这是新设备首次同步时最重要的安全边界。

建议补充三条实际规则。

第一，激活基线只能由一次指定的迁移创建。

迁移端完成旧数据校验后：

创建不可变初始基线并读回验证。

创建引用该基线身份和校验信息的激活记录。

其他客户端只能加入该激活批次。

新设备如果先收到激活记录、尚未收到完整基线，则等待依赖到达，绝不能自行初始化另一份基线。

迁移中断时，不得把半成品当作已激活状态。

第二，曾经激活过的客户端必须记住该事实。

本机暂时看不见 v2 文件，不等于恢复为旧版，也不等于配置被删除。

已激活客户端不能重新导入旧 arrange.md 作为权威。

第三，本机待发送操作必须真正持久化。

新增操作必须完成内容校验、本地持久保存及必要的读回验证，再反馈已在本机保存。

共享文件创建结果不明时，恢复时检查原路径与内容指纹：

内容一致：视为同一次提交。

路径相同但内容不同：隔离冲突。

共享文件尚未到达：使用原操作 ID 重试。

本机持久化失败，不得反馈保存成功。

不建议额外引入全设备 Sync 完成协议。 只需判断当前操作所依赖的基线和前置记录是否已具备。不能因此假设所有远端操作都已经到齐。

4. B4＋C2：明确配置权威范围与事项异常的依赖隔离

这里有两项相互关联的问题。

第一，v2 首版的唯一权威必须限定为已迁移的配置域。

原计划 C2 的「v2数据为唯一权威」建议改为：

v2 是已迁移配置域的唯一权威；事项 Markdown 中尚未迁移的完成、日期、父子、重复及奖励业务事实，仍按现有事项协议维护，不另外制造一个竞争权威。

旧 arrange.md 不再成为配置来源；旧事项 Markdown 的合法更新仍按事项原有边界处理。

否则容易让开发者误以为所有事项状态已经完成迁移，实际却同时存在两套完成状态或钉住状态。

第二，单事项隔离不能简单 catch 后跳过。

目前 arrangeStore.ts:258–267 碰到异常 GVID 可以终止整个事项加载；arrangeStore.ts:329–331 仍可能因配置异常阻止普通业务写入。

这两处必须纳入 B4 的明确整改范围。

建议把以下规则写入 B4：

单事项解析失败、身份缺失或重复 GVID 时，保留原件和错误身份集合；重复身份不得任意选一个作为正确事项。

依据最后可信的事项关系索引，将该事项及确实依赖它的父子完成、目标、重复推进、奖励与汇总计数标为待确认。

对无法确定父子归属的异常事项，不得凭缺失数据确认所有子项已完成。

无关事项仍允许正常勾选、保存和独立业务操作。

5. C4＋D：性能门槛与正式切换顺序需要收紧

这里不是要求增加开发量，而是避免实施顺序产生不必要的新风险。

C4：先规定测试预算，不能测完再主观决定是否可接受。

建议在 A 阶段确定固定的性能测试设备、数据集及预算。至少区分：

iPhone 已同步后的首屏可操作时间。

单项移动到界面反馈时间。

完整轻量索引的计数就绪时间。

数万操作文件的首次同步与后续增量同步时间。

建议以 1万未完成事项＋至少3万操作记录作为首轮压力样本。

可以先以热启动首屏3秒、单项移动反馈500毫秒作为建议目标；最终阈值应在开发前固定，不用这两个数字假冒已经验证的设备能力。

如果超标，先确定瓶颈是全量正文读取、二次复杂度算法、Obsidian 索引还是 Sync 文件管理。不要预先认定只能靠打包解决。

特别注意：如果打包后还永久保留所有原操作小文件，打包本身并不会降低 Sync 需要处理的总文件数。真正减少文件数涉及原记录的安全保留与清理，不能草率实现。

D：已知设备应先升级，再正式激活。

原计划把「切换权威、发布新版、已知设备升级」放在一起，顺序不够安全。

建议调整为：

隔离验证通过 → 发布具备 v2 兼容读取能力但尚未自行激活迁移的客户端 → 确认已知设备升级与旧端待上传数据对账 → 备份并校验正式迁移输入 → 一次性创建 v2 激活记录 → 全端读取同一权威并验收。

如果存在明确无法升级的离线旧端，应将其作为受控的遗留风险，而不是假定它已经停止写入。

0.6.78 Trace 的独立判断

现有阶段0 Trace 对旧配置事故的第一层诊断已经基本足够，不建议再单独安排一轮大型补丁。

五、无法保证的边界

下列限制需要在计划中如实保留：

1. 旧端历史操作不能绝对无损。

尚未升级、长期离线的旧设备，其历史写入如果已被 Sync 合并覆盖，可能无法完整恢复。v2 可以保证旧配置不会重新污染新配置权威，但不能凭空恢复已不存在的操作证据。

2. 尚未迁移的事项状态仍遵循 Markdown 的同步边界。

首版保护单事项异常不导致全局瘫痪，不能因此承诺两台设备同时完成、撤销或编辑同一事项的所有竞争都能自动无损合并。

3. 不能判断从未到达的远端数据。

离线设备可以确认当前本机已验证的数据，但不能据此证明所有远端操作已经完整到达。准确计数必须说明其依据的已验证数据范围，存在已知缺口时不得显示为完整结果。

4. Trace 不等于 Sync 内部审计。

可以进一步定位插件生成、实际提交、写后变化和本机投影之间的故障阶段，但仅凭 GVKit 日志不能绝对证明损坏发生在 Obsidian Sync 内部哪个步骤。

最终独立结论

审核状态：有条件通过，建议修正上述5项后直接进入A批。

本轮没有发现必须推翻「不可变操作＋本机投影＋单次权威切换」的证据，也没有发现必须额外建设同步平台或提前全面重写事项引擎的理由。

最值得优先确保的三件事是：
