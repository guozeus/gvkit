独立校准后的意图是：让单端自动更新、迟到旧配置或单项坏数据只影响确有依赖的状态，其他事项与设置继续可用，并保留现有正确体验。

审核编号：**GVKIT-V2-NOV23-CODEX-REVIEW-FALLBACK**。已读取六份指定资料并核对关键源码；本轮未修改文件、运行测试或发布。

**总体方向成立，但当前计划适合先交付 A 批验证，尚不宜直接交付整轮开发。**“不可变操作＋本地投影＋一次权威切换”针对了已证的共享文件故障面。11/23 仅提醒日期合法变化、排序却从266变277，是强证据；具体首次制造坏字节的环节仍未证，不能归责手机插件或 Sync。

**首版必须修订以下七点。**

1. **把迁移契约提前，纠正 D 的活动顺序。**  
   [计划 D](/root/gvkit/dev/20261123-arrange-v2-execution-plan.md:36) 的“切换后发布”存在窗口风险。应为：隔离验证 → 提交并发布支持 v2 的客户端 → 已知设备实际升级、核对旧端待同步修改 → 保存正式基线 → 单一入口创建激活记录 → 各端在必要基线齐备后采用 v2。  
   激活记录须明确引用哪些基线内容；首版可用一份完整不可变配置基线，避免另造分布式清单系统。激活记录先到、基线后到，或中途退出，都不得采用半套数据。其他端**永不因“没看到 v2”自动迁移**；已激活设备标记暂缺也不退回旧权威。

2. **写定操作身份、自动业务身份和持久化结果，不能只写原则。**  
   普通操作先保存“原 ID＋原内容”的本机待发送副本；共享创建超时或重启后沿原身份核对，不能重新生成 ID。同 ID 异内容按完整业务内容判断，现有 FNV 指纹只用于诊断关联。  
   自动业务键建议固定为“激活批次＋动作类别＋库时区业务日”，旧目标版本等作为**前置条件**，不要放进键里导致同日执行两次。同键同语义合并一次，同键不兼容候选保留局部冲突。特别提醒依赖的是跨天的**逻辑结果**：两端跨天操作物理 ID 不同，不能让后继提醒永久缺依赖。  
   本机耐久保存成功可反馈“已保存”；这不等于已同步到其他设备。共享文件创建回调也不足以证明可清除本机恢复副本。

3. **钉住必须保留显示槽位，rank 可以进一步做减法。**  
   例如 `[A,P,B,C]` 中 P 钉在第2位，把 C 移到最前，仅修改 C 的 rank 会得到 `[C,A,P,B]`，已经违约。  
   最简实现是沿现有语义：投影出固定槽位，把可移动序列填入空槽；rank 如有性能收益再作为缓存，首版不必引入 LexoRank。共享权威仍只有操作。钉住、解钉以及完成后的槽位释放必须进入排序契约，不能用今天的 `pinned` 状态重新解释昨日操作。  
   同时保留源码中的例外：普通移动保护槽位；显式置顶可释放所选事项槽位；每日提醒释放被选提醒的槽位；昨日目标返回则直接插到最前。见 [排序实现](/root/gvkit/src/arrangeCore.ts:129)、[跨天实现](/root/gvkit/src/arrangeStore.ts:307)。

4. **“先跨天后提醒、手工优先”必须成为跨端投影规则。**  
   单机队列先后不能保证另一端收到的顺序。跨天目标返回与移动整条应用；提醒等待必要的跨天结果。迟到自动动作遇到同日手工调序或已选目标，必须按明确规则让位，不能用到达时间或设备钟表判断“较新”。对真正并发的同日手工操作，也应明确人工意图优先于自动整理，并保留被抑制的自动记录。  
   同日提醒候选要限定相关提醒上下文；不能把无关排序变化也算作冲突。只更新处理日期时，零排序操作。时区未确认或冲突时，暂停依赖它的自动域。

5. **新设备的“完整”只承诺可证明范围，旧端自动导入应收缩。**  
   激活基线齐备不代表全部远端操作和事项正文已经到齐。无缓存端展示已到达健康事项；计数只在轻量索引完整时显示该本地数据集的准确值，已知缺资料时不显示正常的0项。正常独立操作无需等待全局 Sync。  
   C2 的旧端差异自动导入应仅限能够证明无竞争的字段，并生成可去重的 v2 操作；不能从旧版全量排序差异可靠反推出全部移动意图。首版允许保存可恢复原件、明确待处理，自动恢复复杂旧排序可后置。旧文件后续变化不得重新驱动新权威。

6. **坏事项不能简单跳过；重复 GVID 的双方都必须隔离。**  
   当前加载会因重复 GVID 整体退出，完成判断则依赖已加载子项，[相关路径](/root/gvkit/src/arrangeStore.ts:258) 确实需要改变。  
   隔离后保留已知身份、关系和原件；父子完成、目标、重复推进、奖励及汇总分别传播“不确定”。没有关系缓存、无法判断坏文件属于谁时，应承认相关汇总或父项资格无法确认，不能宣称其不存在。奖励记录须在身份及实例校验后进入计算，避免坏项被跳过、奖励却已计入。  
   首版无需迁移全部完成和重复历史，但**不能宣称这些 Markdown 状态已获得跨端事务保证**。另外须逐一替换仍直接依赖旧路径的消费者，例如批量置顶读回校验，避免单项操作走 v2、批量操作仍检查旧文件。

7. **性能门槛前移到 A，不能到 C 才决定方案是否可用。**  
   至少在真实 iPhone 上，用 **10,000未完成事项＋30,000操作记录**测冷启动、回访、完整计数、移动保存、首次同步及后台恢复增量；同步到达本身不算性能通过。  
   建议预算：本地数据齐备时冷启可操作≤5秒、回访≤1秒、完整计数≤5秒；连续移动保存 p95≤1秒，界面无持续超过200毫秒的阻塞。固定网络下首次同步和100条增量也须在 A 写定数值预算再实施，不能上线前才解释“可接受”。这些是建议门槛，尚无实测通过证据。  
   若小文件成本超标，可先比较“本机耐久保存后，将短时间内数条操作封成一个只创建一次的不可变包”，保持原操作身份；不能改成每设备每日反复追加一个共享文件。封包对稀疏操作收益有限，未超预算不做完整打包和清理系统。

**Trace 无需再开工程。**0.6.78 已覆盖关键边界；当前缺的是手机实际安装后的现场证据、对应端 Sync Activity，以及未来 v2 的操作／逻辑业务键、基线、隔离和投影结果关联。无需等待再次事故才推进 v2，也无需升级为哈希审计平台。文件观察只能证明“观察到替换”，不能证明替换者；官方也明确说明 Markdown 自动合并可能产生重复或格式问题。[Obsidian 官方说明](https://obsidian.md/help/sync/troubleshoot)
