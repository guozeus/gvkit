# GVKit v2 配置可靠性与局部排序：待独立审核的行动计划

状态：2026-11-23。制作人要求先整理行动计划并主持独立对抗式审核，达成共识后交付，暂不实施v2或触碰正式配置。

## 一、置顶意图和成功标准
继续自然使用 iPhone、iPad、PC 上同一 Obsidian Vault。只有一台设备当天打开、自动跨天和提醒写入、迟到远端坏版本、旧版设备回线、新设备初次同步，都不应使自御整体配置失效、字体恢复默认或所有正常事项禁止勾选。每次提示保存成功前，本机数据已经持久化；不同字段并发修改都应保留，真正冲突不静默丢意图。保留GVID、特别提醒、钉住槽位、每日目标、奖励、重复事项及已正确的UI，万级事项可用。异常记录要能定位本地生成/写入/观察到替换/恢复阶段。
边界：不能让未升级的旧端自动遵守新协议；不能保证自由Markdown正文离线同段冲突绝对无损。第一轮重点保障配置域与局部异常隔离，不重写全部任务引擎。

## 三、按实际验收分批执行

### A. 明确最小存储契约并进行同步可行性验证
1. 分类分离界面偏好、目标及跨天返回、特别提醒日期、奖励开关、未完成事项排序。一个实际修改对应一条独立不可变的业务操作，包含唯一操作ID、格式/激活版本、领域和目标、业务参数、相关因果前提、自动业务幂等键。相同ID和相同内容重试只执行一次；ID相同内容不同必须隔离。操作ID本机落盘后重试复用。
2. 在隔离的真实Obsidian Sync环境验证：每操作独立路径、只创建不重写的Markdown记录可自动到达手机；若用JSON须证明逐设备额外类型设置已启用。测量大量小文件对真实iPhone的同步、索引影响。不预建新的通用同步平台。
3. 一次移动只保存受影响事项的移动意图（事项ID、相邻锚点、钉住槽位、因果基线），由本机投影形成可重建稀疏排序rank。不同时维护可变的rank权威和事件权威。多个特别提醒可一次逻辑操作表达受影响的局部序列。若只是更新当日处理日期，不触碰排序。保留钉住事项固定槽位及原本已正确的每日提醒先后语义。
4. 投影基线+收到的合法操作集合必须确定：收件顺序或设备时钟不决定胜负；无关字段自然合并，同字段/同位置真实并发冲突保留双方，缺因果依赖暂存而非部分应用。验收模拟乱序、重复、断网后重入，结果一致或呈同样冲突。

### B. 制作配置域v2、自动动作及自检/恢复
1. 每条操作先校验并保存本机持久待发送副本，才提示保存；同一设备现有队列串行处理提交与新到达操作。提交与刷新分离，不应只因重复打开而写新文件。
2. 读本机最后可信投影优先显示，启动、恢复前台、新文件变化和提交前后做有界增量校验。不可依赖Sync完成标志作为唯一触发。新设备未收到统一激活记录和完整所需基线时，不能创建空基线；缺数据不是删除，目标、数量等不可确认部分才最小提示待确认，无关事项仍然可用。
3. day_rollover的目标返回及对应排序为一条原子业务意图；每日特别提醒另为一条。以激活批次、库时区业务日、动作种类及原目标上下文作幂等判据，多端或同端同日重复触发只生效一次。先跨天再提醒，迟到自动动作不得覆盖之后手工排序或今日新目标。
4. 任意坏配置操作隔离原件并从合法投影恢复，不能把默认偏好写回云端。一个事项Markdown异常或重复GVID不得导致所有事项加载失败，但它的父项完成、每日目标、计数、奖励、重复等依赖也不得被误判正常。阶段1不强行改写全部完成和重复历史的存储协议。
5. 在既有0.6.78 Trace 上补v2操作ID、基线、投影、隔离及恢复结果等关键事件即可；保留设备本地有界事故证据，失败时可从命令面板导出，不记录点击流水/正文/密钥。

### C. 旧版迁移、真实多端联调、规模门槛
1. 在独立测试环境备份并读取旧配置、事项状态及当前正确顺序，创建一次唯一迁移激活基线。已知旧设备待上传意图先尽可能对账，确认已知端可升级。各新端只加入同一v2基线，不能因暂时没收到新文件各自再迁移。
2. 切换后v2数据为唯一权威，旧arrange.md即使被未升级旧端再次写坏也不影响新版。旧端迟到合法变化可基于切换前后差异无竞争导入一次，冲突/损坏保留原件，不能整份覆盖。产生v2新操作后，不可直接回滚至旧权威以免丢失新意图；需要能读取v2的修正版或无损导出。
3. 真实隔离iOS/iPad/PC/Headless Sync按事故顺序验收：11/22手机先坏而开发机仍好、迟到远端坏版本；11/23只手机进入自动特别提醒；旧端长离线回线；两端不同字段/同字段修改；断电重试；单项损坏及关联父子奖励；新设备分批到达。
4. 测试至少10,000未完成事项和代表性数万操作文件的首屏、准确计数、单次排序、增量及首次同步耗时。若真实测量文件增长导致不可接受性能，须在上线前解决为保留原操作身份的不可变打包；不在未测前建压缩/清理系统。

### D. 正式发布与验收
在隔离环境验证、提交源码、原有重要功能定向核验之后，备份正式旧配置及现有待同步意图；只进行一次v2权威切换，发布GVKit新版。按已知设备完成升级与实机体验，检查字体、默认按钮、目标、特别提醒、置顶/钉住槽位、完成/重复/奖励以及勾选保存、首屏正确计数。没有证据的成功不得宣称，日志可以按设备与写入阶段闭环追踪。

## 四、明确暂不做
不另建服务器、全局CRDT/设备注册平台、完全重写事项引擎、普通正文任意并发自动语义合并、没性能实测就造大规模打包和历史清理、通用哈希审计系统、与当前意图无关的UI改版。

## 五、供审核者核对的核心问题
先独立校准意图；判断是否有被忽略的实际失败路径和过度工程。重点：一次移动局部rank与不可变操作是否双权威；特别提醒/跨天业务幂等是否真实可行；不能全量复制Sync的情况下何时确认新设备基线齐全；单事项损坏的依赖隔离范围；旧客户端未读新激活记录的迟到操作如何处理；小文件规模的最低充分验证；诊断日志能否真正区分候选坏/写后被替换。审查不能故意挑刺，先在最小方案内部找可直接补强之处。
