**2．必须补强的六项**

1. **操作 ID 去重尚不能代替业务幂等和确定性投影。**  
   两端自动跨天会生成两个不同 UUID；若只按 UUID 去重，仍会执行两遍。相反，按日期直接合并，也可能吞掉不同旧目标产生的真实分歧。方案需要写定：同一次重试如何沿用 ID、自动动作如何识别同一业务、因果依赖如何表达、并发动作如何处理。不能按到达顺序、设备时间或目录枚举顺序更新最终状态。

2. **启动缺数据与恢复机制仍缺少明确状态。**  
   “最后有效投影”只能证明过去正确，不能证明今天目标已经确认；“缺文件”也不能证明已删除。特别是新设备没有缓存时，不能将缺配置解释为首次安装，自动生成第二套迁移基线。需要明确待到达、损坏、冲突、未知版本和明确删除的区别，并保证本机尚未传出的操作有独立持久副本。

3. **一次性切换缺少可执行的迁移与回退契约。**  
   旧版本标记只能约束实际读到它、且确实支持拒写的旧代码。迟到旧文件需要基于迁移基线比较，而非整份再导入。主方案“必要时以旧合法版本回退”也需收紧：产生 v2 新操作后，回退旧程序、旧快照可能遗失新成果。

4. **配置免疫不等于事项业务状态免疫。**  
   当前完成、日期、父子、钉住、重复历史和奖励事实仍通过事项 Markdown 重写；普通完成还包含改属性、移动文件和再保存排序等多个步骤。[完成路径](/root/gvkit/src/arrangeStore.ts:477)  
   同时，事项解析失败、重复 GVID 等会直接中断整体加载。[加载路径](/root/gvkit/src/arrangeStore.ts:258)  
   若首版只迁移配置域，必须降低承诺；若保持本轮整体可靠性目标，就必须把插件维护的关键业务状态纳入保护，并实现单事项隔离。

5. **快速缓存解决不了同步层的小文件增长。**  
   每操作一文件会同时增加 Obsidian 索引、Sync 枚举和移动端文件管理成本。当前只有“之后测量再决定”，不足以支撑长期方案。至少需要从首版格式上支持保留原操作身份的不可变打包；不能用随时间删除旧事件来控制数量。

6. **现有 Trace 无法提供要求中的关键证据链。**  
   `ArrangeTrace.record` 会过滤掉全部非异常事件；成功候选、成功写入及普通文件变化均不留存，现有测试也确认这一行为。[过滤逻辑](/root/gvkit/src/arrangeTrace.ts:67)  
   因而“GVKit 生成了什么候选、实际写入什么、之后观察到什么”目前无法连续对照。仅增加异常提示不能解决此缺口。

**非首版必须：**通用 CRDT／同步服务器、自动处置所有正文冲突、语义性删除历史事件、复杂设备注册与确认平台。它们不应成为本次开工前置条件。

**3．最小但完整的修订方案**

**存储与写入。** 保留 GVID 和现有 Obsidian Sync。共享操作放在非隐藏的现有控制目录之下，例如 `settings/gvkit/v2/`；本地待发送副本、投影和诊断使用明确不参与 Sync 的设备本地存储。

首版优先验证“每操作一个不可变 Markdown、内部承载严格结构化数据”。JSON 可以保留为候选，但不能假设各端自动传输：官方要求额外文件类型逐端开启，而且隐藏目录通常不参与同步。[官方同步设置](https://obsidian.md/help/sync/settings)

每条操作最少包含：

| 内容 | 用途 |
|---|---|
| 格式版本、激活记录引用 | 防止混入错误迁移基线或未知协议 |
| 操作 ID、类型、目标事项／实例 ID | 唯一识别操作 |
| 涉及状态的因果基线／父操作引用 | 区分后续修改与并发修改 |
| 必要业务参数、自动动作业务键 | 重建业务结果和逻辑去重 |
| 来源客户端版本、诊断设备标识 | 定位来源；不参与冲突胜负 |

普通操作 ID 可复用现有 `createGvid`。**一次业务提交先生成并保存 ID；重试、恢复、复制传输沿用原 ID 和原内容。** 相同 ID、相同内容只计一次；相同 ID、不同内容必须隔离，不能覆盖。自动操作即使拥有相同业务键，也应使用不同物理操作路径，避免不同候选再次争写一个文件。

写入顺序固定为：校验候选 → 保存本机待发送副本 → 创建共享记录并读回 → 更新投影、反馈已保存。共享写入结果未知时沿原 ID核对。待发送副本的清除不能仅依赖一次文件创建回调；需要经过已定义的恢复安全条件。

**投影与业务幂等。** 复用现有单机队列，让命令提交、接收处理和自动动作串行；读取与刷新本身保持只读。因果信息只覆盖相关状态，不引入全库事务平台。

投影必须是“基线＋有效操作集合”的确定函数：

- 缺父操作或目标资料时暂存整条意图，不能先应用其中一半。
- 已知因果后续可以替代旧值；并发不同字段自然合并。
- 并发同字段不同值保留冲突；暂用共同的已确认值，限制相关字段及依赖操作，不拖垮其他事项。
- 排序按明确锚点和钉住槽位规则重放；并发时使用固定规则，不能使用收到顺序。同一事项或相互依赖锚点产生不可兼容移动时，保留排序冲突。
- 用户解决冲突时生成引用双方的新操作，原记录保留。

自动动作采用以下约束：

| 动作 | 必须固定的语义 |
|---|---|
| 跨天 | 业务键关联目标日期、统一时区规则和原目标版本；目标返回与排序移动是一条意图。同日不同旧目标不得简单吞并。 |
| 特别提醒 | 同一业务日首次整理只产生一次逻辑效果；不同候选须比较上下文。明确先跨天、再首次提醒，迟到记录不能再次覆盖后续手动调序。 |
| 完成／撤销 | 记录明确目标值，不能记录“翻转”。重复实例沿用已有实例 ID；同一实例完成不重复增加历史或奖励。 |
| 每日目标 | 迟到的旧日跨天记录不能清空今天已明确选择的目标。 |

**启动、自检与恢复。** 以启动、恢复前台、相关文件增删改名、提交前后和手动刷新作为触发器；有界合并重复检查，不能只等“同步完成”。现有监听只覆盖事项目录和旧配置路径，新路径必须完整接入。[现有监听](/root/gvkit/src/arrangeView.ts:393)

先展示最后验证投影和本机已保存意图，再增量读取。缺依赖不等于删除；删除应来自明确业务操作。损坏记录保留原件并隔离，能从有效记录重建就自动重建，不能猜测默认值后写回。

每日目标、奖励和计数必须有明确的可信范围：完整轻量索引就绪后，显示该已验证本地数据集的准确计数；已知缺数据或冲突时，不能显示成正常确认值。没有协议可以在离线时证明不存在尚未见过的远端操作，但这不应阻止独立事项正常保存。

**旧版迁移与回退。** 在已知设备的一次受控切换中，核对旧端待同步修改，保存旧配置和事项状态基线；由一次激活动作创建不可变激活记录，其余新端加入同一基线，不能各自因“暂时没看见 v2”而重新迁移。

切换后，新客户端不再把旧 `arrange.md` 或事项中的旧机器状态直接当权威。迟到变更按基线进行三方比较：

- 可确认合法、且没有对应 v2 竞争修改的变更，可以自动导入。
- 导入身份由来源版本及变更目标稳定确定，避免重复扫描重复导入。
- 存在歧义、结构损坏或竞争修改时，保存可恢复原件及候选，等待最小范围确认。

不能从已经损坏或被覆盖的旧文件推导出全部历史操作。对旧端未传出的数据，“已知设备升级／停用旧写入并完成一次对账”仍是最小现实边界。

v2 已产生新数据后，优先使用能读取 v2 的修正版或只读恢复；不得自动退回旧权威。确需降级，应先保全 v2 及新成果，再执行明确的数据导出转换。

**事项与自由 Markdown。** 为满足本轮整体目标，建议首版将插件维护的完成、日期、父子、钉住、提醒、重复实例及历史、奖励事实纳入同一操作投影。完成与重复后继生成等关联变化由一条业务意图决定；文件移动或 Markdown 展示写回只是可重试的派生结果，失败不能撤销已经保存的业务事实。

原 Markdown 正文、GVID 和既有历史保留。若为了现有阅读或查询体验保留属性映射，须明确它是派生显示；用户或旧插件对这些属性的直接编辑走有基线的导入，不得重新成为第二权威。

自由正文继续遵循普通 Markdown 冲突边界；插件编辑也不能用陈旧正文静默覆盖已变化的原文。单文件解析失败、重复 GVID、重复历史异常均应隔离该事项，保留其上次正确状态或可访问原件，并使其余事项继续可用。

**性能与记录增长。** 本地使用 GVID 索引、顺序位置表及增量更新，替代目前的全量读正文和 `order.indexOf` 重复查找；首屏只读必要正文，计数不依赖已渲染行数。[现有排序](/root/gvkit/src/arrangeCore.ts:117)

共享层支持**不可变打包**：将旧操作完整放入新包，保持原 ID、业务参数和因果引用；独立文件与包重复到达仍只计一次。包验证、读回和恢复路径未完成前保留原记录。必须覆盖“先收到原文件删除、后收到包”的顺序，期间不能把状态清空。长期离线端也通过同一包读取器追赶。

快照只加速，不凭创建时间宣称覆盖全部历史；须携带覆盖范围、因果状态、去重信息和未决冲突。首版不做语义性遗忘，不因设备离线久就判其操作过期。是否立即启动打包及阈值，由真实 iOS 文件数量测试决定；**读取格式和正确性规则需先具备。**

**4．诊断日志的最小闭环**

扩展现有 Trace 即可，不建新平台。保留与持久化、接收和恢复直接相关的少量成功边界；不增加普通点击流水。

| 关键事件 | 最小证据 |
|---|---|
| 候选生成／拒绝 | 操作 ID、触发原因、基线、类型、校验阶段、候选字节指纹 |
| 本地保存／共享写入结果 | 同一操作 ID、预期与读回指纹、成功／失败／未知、本地副本状态 |
| 文件变化被观察到 | 观察时间、记录 ID、字节指纹、是否合法；无法识别来源时明确记 `unknown` |
| 旧版导入／隔离 | 来源版本指纹、导入操作 ID、接受或拒绝原因 |
| 投影重建／恢复 | 投影器版本、输入覆盖范围、缺依赖／冲突数量、输出指纹、使用的基线或快照 |

所有事件关联诊断设备标识、插件／Obsidian 版本、会话 ID、单调序号、UTC 时间和时区偏移。跨设备顺序依据因果关系，时间用于查找对应日志。字节指纹用于关联候选与落盘内容即可，不增加签名链或全库哈希审计。

建议初始保留规则为：最近 14 天且总量不超过 2 MiB；异常时冻结相关前后元数据，独立保留最近 3 份事故摘要，避免被正常写入挤掉。数值可按真实开销调整。诊断不保存正文、完整配置、密钥或无关交互；恢复所需业务原件与诊断日志分开管理。

设备上复用现有“复制交互诊断”入口，并提供不依赖自御完整加载成功的命令入口。自动持久保存异常摘要，避免必须在报警当刻复制；导出同时标明持久化是否成功、是否发生轮转丢弃。

**GVKit 不能把普通文件变更事件命名成“Sync 下载成功”。** 当前源码已正确承认来源未知。[来源说明](/root/gvkit/src/arrangeView.ts:54) 精确区分 Sync 内部合并与其他外部写入，仍需对应设备的 Sync Activity、冲突记录及版本历史；官方提供冲突日志查看路径。[官方故障诊断](https://obsidian.md/help/sync/troubleshoot)

现实目标是使下次事故通常能判断“候选已坏／写入不符／写后被外部替换／导入错误／投影错误”，而不是承诺日志永不丢失或百分之百还原 Sync 内部过程。

**5．八个高价值验收场景**

以下是设计审核判断，**不是本轮执行结果**。

| 场景 | 核心通过标准 | 当前方案判断 |
|---|---|---|
| **① 11/22 原时间线**：手机先异常、开发机仍正常，之后迟到坏旧版本；当天不开 iPad | 保住有效显示和独立事项写入；今日目标不假正常；旧坏文件不污染 v2；证据能分辨先后 | 已列场景，恢复与证据契约未闭合，不能判通过 |
| **② 合法输入合并损坏**：UUID 粘连、断裂、重复键及坏单条操作 | 严格拒绝坏候选；隔离坏记录／事项；其余状态可用；不回写猜测修复 | 配置方向可覆盖；事项整体加载失败仍须补 |
| **③ 同日自动动作并发**：跨天、提醒、反复进出、两端首次进入 | 同一业务只生效一次；目标与排序原子；不重复奖励；迟到自动动作不覆盖后续手动操作 | 只有幂等原则，没有完整键和投影规则，未通过设计审核 |
| **④ 操作乱序、重复与中途退出**：子先父后、同 ID 重投、写后未反馈即退出 | 所有端最终投影一致；不重复提交；本机已保存操作重启可恢复 | 内存模型局部支持，真实持久链路未证 |
| **⑤ 旧端离线回线及再升级** | 新权威安全；可确认合法变更只导入一次；歧义保留；不从旧快照覆盖 v2 | 边界表述正确，导入与激活细节不足 |
| **⑥ 同事项多端修改**：完成／撤销、日期／正文、重复实例、父子相互调整 | 不重复实例或奖励；不形成静默父子环；结构化冲突局部隔离；正文竞争可恢复 | 只迁配置不能通过；业务状态迁移需明确纳入 |
| **⑦ 规模与打包**：10k 待办、大量完成历史及至少数万操作 | 实测首屏、交互、完整计数与同步耗时；无全正文读取和二次复杂度；打包乱序不丢数据 | 尚无原生性能证据，不能判通过 |
| **⑧ 安装、升级、异常与原体验**：新端数据分批到达、迁移中断、未知版本、日志存储失败 | 不生成第二基线；不双权威；字体、钉住槽位、目标返回、重复历史等正确体验保留；加载失败仍能导诊断 | 需要新增明确契约并做代表性验证 |

性能验收须在固定真实设备与相同数据集上记录首屏、可交互、计数就绪及同步耗时，并在制作前固定预算；仅说“比旧版快”或“10k 测试通过”没有足够验收含义。

**6．供主控归并的结论**

> 保留“现有 Sync＋不可变操作＋本地投影＋一次权威切换”的方向。开工前补齐六项契约：操作身份与业务幂等、确定性因果投影、启动缺数据及本机恢复、旧端迁移与安全回退、事项机器状态和小文件增长控制、关键写入及异常证据。  
>   
> 首版应保护插件维护的关键业务状态，并明确自由 Markdown 正文的冲突边界；如果只做配置域，必须同步缩小可靠性承诺。采用保留原操作的不可变打包控制文件增长，暂不做历史语义裁剪，不增加服务器或通用同步平台。  
>   
> 当前证据足以支持该架构方向，尚不足以宣布真实 iOS／PC／Headless 多端可靠性或性能已通过。

## 第二轮：压缩首版范围后的独立复核和共识

**最终可行动共识**

支持压缩后的分阶段方案。我修正上一轮建议：**所有事项状态迁移、打包读取实现都不应成为首版硬前置**，否则确有扩大为任务引擎重写的风险。首版可承诺“配置异常不拖垮整体，已验证且依赖完整的事项可继续使用”；不能承诺完成、重复历史及正文并发修改全部无损。

1. **隔离必须覆盖依赖。** 坏事项保留原件，不按不存在处理；相关父子完成校验、重复推进、目标及奖励计算暂不可确认，其他独立事项仍可保存。若只是捕获异常后跳过坏项，可能误判父项可完成、漏计或错发奖励，这是分阶段方案最主要的失败风险。旧配置异常也不能继续成为全局拒写开关。

2. **建议先发一个小幅诊断补丁，不改变业务逻辑，也不等待再次事故才推进 v2。** 最小证据：触发原因、客户端版本、设备／会话标识、run、时间与序号；读取源、生成候选、写后读回的字节指纹及校验结果；随后观察到的文件变化和异常阶段。仅记录关键写入边界，设备本地限量轮转、异常冻结，沿现有入口导出；不存全文、密钥或点击流水。它能区分候选已坏、写入不符、写后变化；没有对应 Sync 日志及原始修订，仍不能证明具体合并主体。

3. **最简幂等合同：**一次提交生成一个操作 ID，持久保存后重试沿用；同 ID 异内容隔离。自动业务键为“激活批次＋动作类型＋库时区业务日”，原目标版本等上下文作为前置条件；同键不同候选保留冲突，不能重复执行。跨天目标与调序原子投影，先跨天、再首次提醒；迟到自动动作不得清空已选目标或重新覆盖手动调序。普通配置操作只携带所改字段的因果基线，同字段竞争局部待确认，无需全局 CRDT。

4. **版本缺失合同：**已激活设备记住 v2，标记暂缺不能退回旧权威；新设备未取得有效激活记录及必要基线前，不自动迁移、不写空基线、不运行依赖它们的自动动作。未知版本保留并限制相关域。

5. **首次同步的可用性：**已有健康数据可阅读；依赖完整的独立操作可保存。无缓存时显示简短“正在载入”，缺资料的目标／计数显示“待确认”，不能显示空库、零事项或“今日正常”。不强制全局等待同步完成，也不把未到达当删除。

6. **增长控制：首版不必执行打包。** 格式保留版本、操作身份与去重语义；测量真实 iOS 下 10k 事项及代表性操作增长的启动、索引和同步成本，固定性能预算及触发门槛。超预算则打包成为发布前必要工作；未超预算可后续实现。首版不删除历史事件、不提前造压缩平台。

**仍有分歧／验收边界**

对上述分阶段范围无原则分歧；我反对把“整体可用”扩写成“所有业务状态永不冲突”。首版必须验证：11/22迟到坏版本、同日自动动作重复、旧端回线、坏事项依赖隔离、新端分批到达及10k性能。配置新权威不得受旧文件污染；旧端合法变更尽力恢复，歧义保留。
